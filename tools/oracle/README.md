# Differential oracle harness and byte-parity corpus

Wayfinder ticket [#13: Differential oracle harness and
byte-parity corpus](https://github.com/mestrode/triangle/issues/13).
This is the gate the port plan is built on: the strategy decision
([ADR 0001](../../docs/adr/0001-port-strategy.md), closed tickets #5, #6)
fixes byte-identical outputs against a pinned C oracle as the binding
correctness gate for the Rust port, permanent on the serial path, also under
later internal multithreading.

Everything here is designed so a single command runs the whole gate:

```sh
tools/oracle/run-harness.sh                        # self-check (default)
tools/oracle/run-harness.sh --candidate BIN        # differential run vs a port
```

Prerequisites: a C compiler (cc/gcc/clang), Python 3 (stdlib only; 3.8+
tested), POSIX sh. All work products land under `tools/oracle/work/`
(git-ignored) and are fully regenerable from the committed scripts.

## Pinned C oracle build recipe

`build-oracle.sh` compiles the repo's own C sources (core library plus the
triangle-cli example) into `work/oracle/triangle-oracle` with the flags
pinned by the oracle determinism findings:

```
-O2 (default; -O3 accepted via TRIANGLE_ORACLE_OPT), -ffp-contract=off,
no -march/-mtune/native overrides, 64-bit target
```

Rationale (findings doc for ticket #5, branch research/oracle-determinism):
the algorithm itself is deterministic (platform-independent integer LCG,
no time/env dependence, allocation-order output numbering); the only real
cross-build divergence risk is FP codegen. Disabling FMA contraction on the
C side pins f64 arithmetic to plain IEEE 754, matching Rust's default
`--release` codegen, so byte-identical outputs are a realistic target.

The recipe is independent of CMake on purpose (CMake does not pin
-ffp-contract); the two build-generated headers (`triangle_version.h`,
`triangle_export.h`) are produced locally, with aCute compiled IN (no
`NO_ACUTE`). `work/oracle/build-info.txt` records compiler, architecture,
flags, source hashes and the binary sha256; re-running the script on the same
machine reproduces the same binary hash. Cross-machine reproducibility is not
claimed or needed: the harness re-runs the oracle whenever its sha256 changes
(the cache is keyed by it).

## Corpus

`generate_corpus.py` generates, deterministically and seeded (never
committed; regeneration is byte-identical, verified by the self-check):

- five case classes in three sizes each (15 cases):
  `grid` (integer lattice with square hole; collinear/cocircular degeneracy
  stress), `random` (random point set), `pslg_hole` (unit square with
  square hole ring), `pslg_concave` (L-shape), `pslg_wall` (unit square
  with an interior wall segment);
- crossed with the full option family (180 runs):
  plain Delaunay (`""`), constrained (`-p`), quality refinement without
  aCute (`-q20` on the point set, `-pq20` on the PSLG), quality with aCute
  (`-pq20U120`, the aCute max-angle `-U` switch), fixed area constraints
  (`-pa<area>`, `-pq20a<area>`), `-pen` (also writes .edge/.neigh), and the
  -r refine families reading pre-existing meshes (issue #68): `-r`
  (reconstruction only), `-rq20` (quality refinement on the existing mesh),
  `-ra<area>` (area-constrained refinement), `-rpq20U120` (the aCute variant
  over a segmented base mesh).

Each case produces `input.node` and `input.poly`, the sealed -r base
meshes (`rbase-plain/` from the plain family, `rbase-p/` from the p family;
built by one pinned-oracle run per case, issue #68) plus a manifest
(`work/corpus/manifest.json`) with per-file sha256 hashes (base meshes
included) and per-family argv. Area targets scale with domain area and size
class so element counts (and runtimes) stay comparable. An opt-in size class `xl` exists for the
performance gate (\#11): it is generated separately (`--sizes xl`, e.g.
`--out work/corpus-mt`) so the default corpus stays the sealed 180-run
parity contract.

## Differential harness

`diff_harness.py` (invoked through `run-harness.sh`) runs the oracle and
the candidate over every (case, option family) pair and compares the outputs
byte-for-byte: `.1.node`, `.1.ele`, `.1.poly`, and `.1.edge` /
`.1.neigh` where the family produces them.

The -r families (issue #68) read pre-existing meshes: the generator seals
each case's base meshes into the corpus (one pinned-oracle run per case over
the plain family, or the p family where segments are required), and the
harness stages the family's multi-file input set (`node + ele + poly` as the
family requires) into every run dir, identically for oracle and candidate;
the file and stdout gates apply to the new families unchanged.

Candidate contract: an executable with the triangle-CLI interface. The
harness invokes it as `./candidate <options> <input>` inside a fresh run
directory that already contains the input files. Both oracle and candidate
are always invoked through a symlink named `candidate` so the
`# Generated by ...` trailer the C writers embed matches byte-for-byte
too. The candidate must exit 0 and write the outputs with the standard
`input.1.<ext>` names. Every run's env carries `ORACLE_HARNESS_CASE` and
`ORACLE_HARNESS_FAMILY` (used by the stub; a real candidate ignores them).

Exit codes: 0 = corpus green, 1 = mismatches found, 2 = harness/config
error. A JSON report is written to `work/reports/last-run.json`
(overridable with `--report`).

### Bisection workflow (first-divergence localization)

On mismatch the harness reports exactly what a function-per-function port
mapping needs (see ADR 0001: strict mapping is what makes this bisection
possible at all):

- which case (and its kind/size), which option family (the exact flag
  string), which output file;
- the first differing byte offset, line number and column;
- both diverging lines, verbatim;
- three lines of context on each side.

Filters narrow the run to a kernel while bisecting:

```sh
tools/oracle/run-harness.sh --candidate rust-triangle --case pslg_wall_l --family 'pq20*'
```

Oracle outputs are cached under `work/cache/<oracle-sha>/` and reused, so
repeated candidate runs take one corpus pass.

### Harness validation (injected divergence)

Since no Rust port exists yet, the harness is validated against a
deliberately diverging candidate: `stub_candidate.py` runs the real oracle
(argv passed through exactly, including the header trailer), then perturbs
one value in one output file of one designated run. The default self-check
wires it and asserts, end to end, that the harness detects the divergence
and reports precisely the injected location - and, as a second flavor, that
a missing expected output file is flagged as such:

```sh
tools/oracle/run-harness.sh
# [ok] corpus regeneration byte-identical for all 15 cases
#      (geometry inputs and -r base meshes)
# [ok] oracle self-determinism: ... byte-identical for all N runs
# [ok] injected divergence detected and localized: case random_m, family pq20,
#      file input.1.node, first differing line 6
# [ok] missing-output divergence detected: case grid_s, family p, file input.1.ele missing
```

The self-check also proves the pinned oracle is self-deterministic over the
whole corpus (two passes, byte-compared) and that the corpus generator
regenerates byte-identically.

## Wiring

- Stage-1 verification (transliterated core + CLI): every implementation
  PR runs `tools/oracle/run-harness.sh --candidate <path-to-rust-cli>` and
  must be corpus-green before review; the PR references this ticket (#13).
  The Rust CLI is invoked exactly like the C CLI (same options, same .node/
  .ele/.poly writers with %.17g), which the I/O phase of the port provides.
- Idiomatization rungs (ADR 0001: rungs 1-4): same gate, same command, re-run
  on every rung step. A rung that cannot keep the corpus byte-identical does
  not land.
- Permanent serial-path CI gate: `.github/workflows/oracle-harness.yml` runs
  the harness self-check on every push and pull request (oracle determinism
  plus the harness itself). Once the Rust port exists (stage 1 + I/O + CLI
  phases), switch the CI job to the differential command with the built
  Rust CLI as the candidate; from then on that job IS the permanent serial
  byte-identity gate. The serial path stays bound to byte-identity even
  after multithreading lands (parallel variants are validated structurally
  and for scaling; deterministic parallel scheduling is handled in its own
  wayfinder ticket).
- Corpus hand-off to the performance gate (#11): the benchmark corpus IS
  this corpus. `generate_corpus.py` is the single source; the manifest's
  seeds and hashes pin identical inputs for benchmarking. The performance
  gate extends it with MT variants (larger size classes and thread-axis
  cases generated the same seeded way) rather than replacing it;
  single-threaded parity in #11 compares against the same
  `build-oracle.sh` binary.

## Performance gate (#11)

The benchmark corpus IS the harness corpus: `run-bench.sh`/`bench.py` time
whole-process wall time over exactly those (case, family) runs, under the
harness's own invocation contract ('./candidate <options> <input>', symlinked,
stdout to file). ADR 0001's single-threaded parity goal is therefore a single
documented command:

```sh
tools/oracle/run-bench.sh --candidate <rust-cli> --gate 1.05
```

Configuration (ticket #11): the timed set is sizes m and l of every case
class x option family (120 timed runs at the 12-family corpus since the -r
extension, issue #68; 80 runs before it); size s stays corpus-only, its runs
are startup-dominated and measure process overhead, not the meshing kernels.
Per timed entry, oracle and candidate runs interleave: 3 warmup runs per
side, then 25 timed runs per side; the per-side statistic is the median.
Binding numbers: the sum-of-medians total ratio and the geometric mean of
per-run ratios, both within the tolerance (1.05), plus a per-run ceiling
(1.35) as a regression tripwire. The tolerance is not a guess - it is bounded
below by the measured noise floor of the gate machine: pointing
`--candidate` at the pinned oracle itself measures the ratio distribution
around 1.0, and on the 2-vCPU build server the aggregate total ratio stayed
within about +/-1.6% across repeated probes (single-run CV ~15%; worst
per-run median-of-25 ratio 1.16). A failed gate may be rerun once, binding
on the rerun. Re-derive the tolerance with the same noise probe whenever
the gate machine changes.

MT variants: `--threads N` passes `TRIANGLE_THREADS=N` to the candidate only
(the pinned C oracle is single-threaded and ignores it). MT scaling is
measured against the SAME candidate at N=1 (the single-threaded Rust
baseline), never against the C oracle; the MT timed set is sizes l and xl;
each thread-count variant is pinned to N vCPUs via `--pin` (taskset). The
serial path stays byte-identical in any case (the permanent gate;
MT-output equivalence follows the parallelism determinism ruling, ticket
#12). Hardware for the MT axis is a separate, still-open user decision
(see ticket #11).

Invocation schedule (ADR 0001): the gate runs at stage-1 completion, at
every idiomatization rung boundary (rungs 1-4, before a rung lands), and as
the end gate - with the serial byte-identity gate (`run-harness.sh`)
running at all of those points regardless.
